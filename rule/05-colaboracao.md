# 05 — Colaboração

Como o grupo trabalha no repositório sem pisar no trabalho um do outro.

## Uma tela por vez

- Trabalhe **uma tela por vez**.
- Só avance para a próxima depois da **aprovação** do conteúdo e da implementação combinada pelo grupo.
- Não abra várias páginas “pela metade” na mesma entrega, salvo combinado.

## Avisar antes de alterar

Antes de mudar **qualquer arquivo**, avise no canal do grupo:

- qual arquivo;
- o que vai entrar ou sair;
- se alguém mais está usando aquele arquivo.

Isso vale também para `style.css` e para o menu: uma alteração global afeta **todas** as páginas.

## Git

- Commits **pequenos**, com mensagem em **português**, descrevendo o motivo (ex.: `Adiciona formulário da calculadora em agua.html`).
- Não quebrar a **branch principal**. Evite commits direto nela se o grupo estiver usando branches por tela; se trabalhar nela, puxe as atualizações antes e não reescreva o histórico.
- **Teste no navegador** (links, layout no celular e no computador, calculadora se for o caso) **antes** do `push`.
- Conflitos de merge: **resolvam em conjunto**. Não descarte o trabalho de outra pessoa sem conversar.

**Sugestão:** nome da branch principal costuma ser `main`. Confirme no repositório (`git branch`) antes de orientar o grupo.

## O que não fazer

- `push` de página que não abre, com link quebrado ou sem o CSS/JS correspondente.
- Reescrever o arquivo inteiro de outra pessoa para “organizar” sem avisar.
- Mensagem de commit genérica demais (`update`, `ajustes`, `aaa`).
